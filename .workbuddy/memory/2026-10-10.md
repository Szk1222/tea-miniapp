## 排查「开发者工具编译后看不到新内容」

### 根因（三条叠加，都不是编译问题）
1. **端上 Storage 缓存回灌**：`app.js onLaunch` 第一步 `contentClient.bootstrap()` 从 `tl_content_v1` 读缓存并 `overlay.apply()` **就地覆盖** `data/*.js`。devtools 里存着 10-08 的 v3 旧 payload → 新写的 23 茶方/35 食材/36 FAQ 被换回 18/28/10。

3. **`refresh()` 被 AI 开关闸住**：`if (!store.getAiEnabled()) return skipped`，而 AI 默认关闭 → 即使服务端有新版也不会去拉。

### 处理
- **归档旧快照** → `server/storage/_archive/content.stale-v3-*.json`。
- **踩坑**：第一次想走「启动服务端 + `POST /api/admin/reseed`」修复，结果 reseed 出来的仍是 `teas:18, catalog:28, faq:10` —— 因为**服务端启动时旧 payload 已就地污染了内存里的 `data/*`，reseed 只是把污染后的内存再快照一遍**。正解：**先移走 content.json 再启动**。移走后服务端 `init()` 自动播种 → v1，counts = teas 23 / ingredients 35 / faq 36 / catalog 35。

## 排查「推荐的茶方下面又标它忌用」

### 根因：不是知识库内容冲突，是**推荐排序策略**的缺陷
`engine.recommend` 用的是「权重 − 惩罚分」单值排序：
- 结构加分：本体质 +30、当季 +14；惩罚分：禁用 80 / 忌用 60 / 慎用 24。
- 于是 `100+30 = 130 − 60 = 70`（忌用）**反超** `100−24 = 76`… 更糟的是**兜底补齐不过滤风险**，把慎用茶塞进推荐。
- 实测（湿热质 + 经期）：池子里只有 2 款 shire 茶（金银花菊花、蒲公英玉米须），都因寒凉标「忌用」，仍然被推；第 3 款由平和质兜底补上「玫瑰陈皮茶（慎用）」。**三款推荐全是需留意/忌用** —— 用户看到的就是「推荐它、又说它忌用」。

### 修复
1. **`RISK_BLOCKED = ['禁用','忌用']` 一律不进推荐池**；新增 `engine.recommendFull()` → `{picks, blocked}`，`recommend()` 保持旧签名只返回 picks（服务端两条链路没传 basic，行为不变）。
2. **排序改二级**：先按风险档位（无=0 / 咨询医师=1 / 减量=2 / 慎用=3），再按权重。杜绝「加分抵消惩罚」这类隐蔽 bug。
3. **兜底补齐同样过滤**禁用/忌用。
4. **结果页新增「当前情况下不建议饮用」区块**：把被排除的茶方连同原因列出来（不静默删除，否则用户以为库里没有），并在下方说明「特殊时期结束/用药调整后再回看」。推荐区标题由 `{{seasonName}}适配茶方` 改为 `{{c.name}}适配茶方` —— recommend 并不按季节硬筛（只是 +14 加分），写「秋季适配」而列出夏季茶本身就是标题撒谎。
5. `utils/agent.js` 两条链路（MY_TYPE_RE 与 finishRecommend）适配 `recommendFull`：空推荐时给「为什么没有」的说明，有被排除项时单独提示。

### 连带发现并修复：条件性禁忌被写成了无条件禁忌
15/23 款茶方带「经期」标签，其中 **5 条理由写着「经量多者暂缓」却无条件命中**（玫瑰陈皮茶、姜枣暖阳茶、玫瑰桂花茶、玫瑰佛手茶），甚至**玫瑰山楂茶把「量多者暂缓」标成了 `忌用`**。
后果：任何经期用户都被全库拦下，**平和质女性一款干净的都挑不出**（3 款平和茶全慎用）。
修法：禁忌条目新增扁平字段 **`mensesOnly`**（如 `'经量偏多'`），`hitContraindications` 里 `c.mensesOnly && basic.menses !== c.mensesOnly → 不命中`；玫瑰山楂茶 忌用→慎用（使等级与其自身理由一致）。`content-schema.js` 同步声明该字段（**必须声明，否则后台表单保存时会把未声明字段静默丢掉**）——用扁平 enum 而非嵌套对象，正是为了避开这个坑。

### 验证

### 收尾踩坑：版本号碰撞
清空 `content.json` 重启后 `init()` 从 **1** 重新播种，而此时端上可能已经缓存过「v1（旧数据）」→ 两边版本号相同 → `payloadFor` 判定 `unchanged` → **永远拉不到修正后的内容**。补调一次 `POST /api/admin/reseed` 把版本推到 **2**，再用「旧客户端带 version=1」的方式实测，确认返回 `unchanged:false` + 新 payload（玫瑰山楂茶 经期=慎用 / mensesOnly=经量偏多）。
**规则**：端上按版本号相等判断「无需更新」，服务端版本必须单调递增，清空 storage 属于危险操作。
